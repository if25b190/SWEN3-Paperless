# Changelog

All notable changes to the Paperless OCR worker are documented in this file.
The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).

## [0.0.3-SNAPSHOT]

### Added
- New standalone Spring Boot (Kotlin) application `paperless-worker` that runs the OCR worker
  service. It consumes `OcrRequest` messages from the RabbitMQ queue `paperless.ocr.requests`
  (exchange `paperless.ocr`, routing key `document.uploaded`) that the backend's dispatch
  scheduler publishes after a document upload.
- Anti-corruption layer for the `documents` table, mirroring the backend's layered architecture:
  the service only sees the narrow `WorkerDocument` domain model; `OcrDocumentPersistence` is the
  domain-facing interface and `JpaOcrDocumentPersistence` the `@Repository` adapter that keeps
  `WorkerDocumentEntity`, the Spring Data repository, and the pessimistic row lock behind the
  boundary. Entity ↔ model mapping is generated by MapStruct
  (`WorkerDocumentEntityMapper` in the same shape as the backend's `TeamEntityMapper`:
  `toModel` / `toEntity` / `applyTo`, `componentModel = "spring"`, constructor injection,
  `unmappedTargetPolicy = ERROR`).
- `OcrWorker` Rabbit listener (`ocr/worker/`) with `autoStartup` bound to `paperless.worker.enabled`
  so the queue is only consumed when the worker is explicitly enabled. The listener binds the
  wire format `OcrRequestDTO` (`ocr/dto/`) and maps it to the `OcrRequest` model through
  `OcrRequestMapper` (`ocr/mapper/`) in the same style as the backend's `TeamMapper`
  (MapStruct, `componentModel = "spring"`, constructor injection, `unmappedTargetPolicy = ERROR`),
  so the service layer never sees broker DTOs. The worker's message converter uses
  `TypePrecedence.INFERRED`, so the listener's parameter type wins over the `__TypeId__` header
  the backend's publisher stamps onto each message.
- `OcrRequestDTO` is generated from `src/main/resources/openapi.yaml` — the broker message
  contract for the `paperless.ocr` queue — with the `org.openapi.generator` Gradle plugin
  (`kotlin-spring`, models only), mirroring the backend's `openApiGenerate` task: the generated
  sources are added to the main source set, and `compileKotlin` / `kaptGenerateStubsKotlin`
  depend on `openApiGenerate`. The model-only restriction skips the generator's API support files
  (`ApiUtil`, `Exceptions`, `SpringDocConfiguration`), which would not compile without a web
  stack. `swagger-annotations-jakarta` is added for the generated `@Schema` annotations.
- `OcrProcessingService` / `OcrProcessingServiceImpl` (`ocr/service/`) implementing the
  claim → extract → complete/fail flow. The service is intentionally **not** `@Transactional`
  because the Ghostscript/Tesseract run takes seconds to minutes and must not hold a database
  connection open; each persistence call opens its own short transaction.
  - `claim(documentId)` moves the document `PENDING → OCR_IN_PROGRESS` under a
    `PESSIMISTIC_WRITE` row lock (the same `findLockedById` + `applyTo` + flush pattern the
    backend uses), which gives at-least-once delivery idempotency: a duplicate job for an
    already-claimed document is skipped instead of reprocessed.
  - On success the document is written with the extracted `ocrContent` and the configured
    `finalStatus` (default `COMPLETED`).
  - On failure the document is marked `FAILED` and the exception is rethrown so the message is
    retried and, after exhaustion, routed to the `paperless.ocr.failed` dead-letter queue.
- `TesseractOcrEngine` (`ocr/engine/`) implementing the `OcrEngine` port. It rasterizes each PDF
  page to PNG with **Ghostscript** (`gs -sDEVICE=png16m -r<DPI>`) and then runs **Tesseract**
  (`tesseract <png> <out> -l <languages>`) on each page, concatenating the per-page text. Both
  binaries are resolved from `PATH` and invoked with a configurable per-process timeout.
- `WorkerDocumentEntity` / `OcrDocumentPersistence` / `JpaOcrDocumentPersistence` /
  `OcrDocumentRepository` (`ocr/entity/`, `ocr/persistence/`) giving the worker its own narrow
  view of the `documents` table so it can claim, complete, and fail documents without depending on
  the backend's feature code.
- Configuration via `paperless.worker.*` (`ocr/config/OcrWorkerProperties.kt`): `enabled`,
  `storage-dir` (default `/tmp/paperless-documents`), `tesseract-languages` (default `eng`), `dpi`
  (default `300`), `process-timeout` (default `120s`), `final-status` (default `COMPLETED`), and
  `index-name` (default `paperless-documents`).
- Elasticsearch indexing of OCR results for full-text search. After successful text extraction the
  extracted text is indexed **before** the document is marked complete, so a `COMPLETED` document
  always has a search entry. Cross-store access follows the repository's layered architecture:
  `OcrProcessingServiceImpl` depends on the domain-facing `DocumentIndexPersistence` port, and the
  `ElasticsearchDocumentIndexPersistence` adapter (`ocr/persistence/`) uses the auto-configured
  `ElasticsearchClient` (`spring-boot-starter-elasticsearch`; connection from
  `ELASTICSEARCH_HOST`, `ELASTICSEARCH_PORT`, `ELASTIC_USER`, `ELASTIC_PASSWORD` via
  `spring.elasticsearch.*`). The index `paperless-documents` (configurable via `OCR_INDEX_NAME`)
  stores one document per `documentId` — `IndexedDocument` (`ocr/model/`) with `id` (keyword),
  `content` (text), and `indexedAt` (date) — and is created at startup if missing
  (`ensureIndex`, whose failure is tolerated so a temporarily unavailable cluster does not block
  worker boot). A failed index run marks the document `FAILED` and the message retry reprocesses
  and reindexes it; indexing by `documentId` is idempotent. The compose stack adds a single-node
  `elasticsearch` service (security disabled, data in the `elasticsearch-data` volume) that the
  worker depends on.
- RabbitMQ listener configuration (`ocr/config/OcrWorkerRabbitConfiguration.kt`) with retry
  (3 retries, exponential backoff) and `default-requeue-rejected: false` so failed messages reach
  the dead-letter queue rather than looping.
- `Dockerfile` (multi-stage) installing `tesseract-ocr`, `tesseract-ocr-eng`, and `ghostscript`
  into the runtime image, running as a non-root `spring` user.
- Test suite: `TesseractOcrEngineTest`, `JpaOcrDocumentPersistenceTest`,
  `OcrProcessingServiceImplTest`, `OcrPipelineIntegrationTest`, `WorkerApplicationTests`,
  `ElasticsearchDocumentIndexPersistenceTest` (mocked `ElasticsearchClient`), and the gated
  `ElasticsearchIndexingIntegrationTest`, which runs against a live Elasticsearch when one is
  reachable at `ELASTICSEARCH_HOST`/`ELASTICSEARCH_PORT` and is skipped otherwise.

### Notes
- The worker shares the `document-files` volume with the backend at
  `/tmp/paperless-documents` and reads uploaded files by `storageKey`.
- The backend's built-in `OcrWorker` scaffold (and its `OCR_WORKER_ENABLED` property) was removed
  from `paperless-backend`; this application is the only consumer of `paperless.ocr.requests`.
